## Shared subsystem shape

These files form a release-evidence and Android acceptance toolchain, not a game runtime. Most validator/compiler scripts consume strict JSON and stable bounded file readers, validate candidate/evidence identity, and produce reports or atomically published manifests. The shared base is `stable_file_reader.py`: lexical/no-follow directory traversal, stable bounded reads, inode/hash checks, JSON publication, file/directory transactions, rollback, and cleanup (`StableFileError`, `open_directory_descriptor`, `consume_regular_file`, `atomic_write_bytes`, `atomic_publish_files`, `atomic_publish_directory`; lines 16–2535). `strict_json.py` layers duplicate-key, non-finite number, UTF-8/BOM, byte/depth/integer-size and object-shape rejection on that reader (`loads`, `load_file`, `loads_matching_object`; lines 20–219).

The acceptance chain statically resolves as: screenshot capture → raw sidecars/session → curation → device acceptance/compiler → human review/compiler → installed identity records/matrix → Play-delivery evidence → governance evidence → readiness gate/evidence index. Asset and package checks feed release preparation. Candidate claims are data-integrity checks, not proof that a device, Play track, reviewer, legal approval, or real-world user experience existed; only corresponding source evidence can establish those facts.

## Source-derived maturity, integration, and limits

1. **The workflow is a release evidence pipeline with human claims as inputs.** Compiler scripts hash/reference drafts; validators check internal structure, cross-manifest consistency, evidence file identity and candidate binding. They do not acquire external Play delivery, device testing, legal review or accessibility observations. `validate_installed_candidate_identity.py` explicitly forbids asserting a specific Play track from device package state, and governance validators retain human approval domains.
2. **A release gate has strong filesystem/integrity controls but does not substitute for execution evidence.** Safe paths, bounded reads, symlink/hardlink checks, content hashes, atomic multi-file/directory publication, strict JSON and candidate SHA checks recur across modules. The behavior of these controls is source-inspected; their runtime effectiveness was not tested here.
3. **There are multiple levels of candidate binding.** Some tools consume caller-provided candidate SHA; other paths require local clean `main`, and evidence validators bind candidate SHA, artifact bytes, signing certificate, APK/evidence files and manifest source bytes. Those are distinct contracts; one does not establish the others.
4. **Visual comparison is diagnostic.** `compare_visual_regression.py` computes pixel difference metrics, while curated set validation handles file structure and human acceptance handles actual review. No threshold in a visual diff is equivalent to user approval.
5. **Static resource validators do not show runtime compatibility.** PNG/font/audio inspection and package page-size/native payload classification can reject structurally bad inputs, but they do not render/play assets or test an APK/AAB on target Android devices.
6. **Script invocation side effects are material.** `capture_store_screenshots.sh`, `prepare_main_release.sh`, `prepare_play_release.py`, `generate_store_assets.py`, `import_final_assets.py`, metadata finalization, publishers and compilers may build, touch device state, create or replace artifacts, or publish evidence.
